# 全局 Docker 部署与环境依赖避坑指南

本文档总结了执行跨机器或远端云服务器 Docker 一键发布更新前，必须遵循的标准工作规范。旨在通过本地验证拦截因为环境缓存未打破或代码引入隐性包丢失，而造成的部署崩溃或服务器排错闭环。

## 核心法则 1: 打破 Docker 的致命缓存机制 (Cache Busting)

在进行 Docker 镜像构建（Build）时，Docker 引擎默认对比依赖清单文件（如 `requirements.txt` 或 `package.json`）字面差异，如果文件未经修改，引擎会**强制调用已有缓存层**。这就导致开发环境即便执行无数次 `pip install` 的升级，打包出来的依然为远古旧版环境。

**规范建议：**
* 开发如需进行重构或大版本升迁，**绝对不可将版本推测权交由构建期处理**（避免只定义如 `>=2.0.0`），务必在工程依赖配置文档中将其修改锚定为具体的固定版本号（如：`==2.5.14`），或新增明确依赖。
* **文件实质内容的变更，是打穿 Docker 旧缓存并使其重新触发在线拉取的根本触发器。**

## 核心法则 2: 拒绝云端“试毒”，在本地集装箱内部做秒测

发现报错加依赖 -> 耗时重推云端拉取 -> 下一报错漏网... 该过程耗时且存在无止境低效循环隐患。

**规范建议：所有的“试毒排雷”操作，必须在本地刚刚构建的最热乎镜像壳内一次性排除！**

在执行最终 `docker push` 发布上云**之前**，建议进行沙盒压测：
1. **钻入沙盒环境** 
  运行所构建的本地容器控制台交互模式（挂载对应核心环境变量文件）
  例如: `docker run --rm -it --env-file .env <IMAGE_NAME>:<TAG> /bin/bash`
2. **肉身试错法**
  直接在内部控制台人工拉起进程命令（例如 `fastapi run main.py`）。所有深层隐藏模块（例如通过字符串引入或者隐式框架反射缺失的插件）的 `ImportError` 或 `No module named` 报错会即刻呈现。
3. **当场补装排查**
  当即执行 `pip install XXX` 安装所缺失内容直至应用最终提示 `Application startup complete.` 或其生命周期等效成功横幅，结束循环修补。
4. **收尾与反哺源文件**
  必须将刚才填补装漏的所有组件老老实实手写补充回宿主机侧的依赖配置文件。继而执行最后一次构建，彻底打包为金牌无错包。

## 核心法则 3: 服务器落地与文件挂载隔离准则

容器封装的仅仅是程序自身依赖。但通常项目均存在配置信息与代码独立隔离。

**规范建议：**
如果在代码开发经历了中大型结构拆分，上服务器执行最终拉取镜像之前必须：
1. **拉取基础设施文件结构配置**：执行宿主机上的版本主支同步更新操作，确保最新的 `docker-compose.yml` 配置对齐以保障目录挂载卷有效。
2. **手动对齐私密环境变量**：仔细比对新代码树带版的 `.env.example`，人工补齐服务端被隐藏由于安全原因而被 Ignore 的实体 `.env` 内部参数（尤其是当引入了新的 LLM Key 或是基础密钥服务名）。如果不做，即使是完美镜像仍会由于获取参数为空值导致服务内部崩溃。
